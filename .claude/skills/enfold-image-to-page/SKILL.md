# Enfold 設計圖 → 直接在後台製作

一般流程是設計圖 → JSON → 短碼檔 → 人工貼上。這個 skill 是捷徑：看設計圖 → 進後台寫入短碼 → 回前台比對 → 有落差就修到一致。少了人工檢查那一關，所以內容規則要自己顧好。

## 使用前提

- 有後台網址、帳號、密碼，以及目標頁面（名稱或 post ID）。
- 有設計圖（一張長圖或多張分段截圖）。
- 環境能操作瀏覽器（瀏覽器工具或電腦操作），能登入後台。
- 主題確認是 Enfold（編輯器有「Advanced Layout Editor」按鈕、短碼是 `[av_xxx ...]`）。不是 Enfold 的話，短碼對照不適用，其他規則仍然適用。

## 核心規則（都是實際踩過的坑）

1. **寫入頁面內容優先用 REST API，不進 Advanced Layout Editor（ALE）按儲存。** ALE 常存著一份和文字內容不同步的舊版積木資料；從那裡存檔，或草稿頁的 heartbeat 自動儲存，都可能把剛寫好的內容蓋掉甚至清空，而且不會有警告。做法見 `references/rest-api-write.md`。頁面是全新空白頁、風險低時，才考慮用編輯器的「文字」分頁貼上後按「更新」。
2. **不要擅自改變頁面的發布狀態。** 新頁面維持草稿，等使用者確認再發布；已上線的頁面寫入時不要帶 `status: 'draft'`（會讓線上頁面下架）。
3. **文案逐字照抄設計圖**，不摘要、不改寫、不翻譯，也不自己補行銷文案。
4. **Hero（首屏主要區塊）一定要有完整內容**，不能開了區塊沒放文字和按鈕——前台會變成一大塊空白，這是最常見的錯誤。
5. **備註、待確認事項、「看不清楚」這類標記，絕不寫進會顯示在頁面上的欄位**（heading、body_text、button_label）。寫進短碼就會原封不動顯示給訪客。看不清楚的地方留空，完成後在回覆裡告訴使用者。
6. 色票用目測換算成最接近的 hex 即可。圖片是灰底佔位圖時，網址留空，不編造網址。
7. **短碼屬性用單引號包住**；內文本身有單引號要換成「’」，方括號 `[` `]` 換成全形「［」「］」。不然短碼解析會靜默斷掉，後面整段內容消失，而且沒有任何錯誤訊息。
8. **寫入前整份自我檢查**：每頁 Hero 有沒有內容、每個文字欄位是否只有正式文案、短碼標籤是否配對。全部通過才寫入，不要邊做邊寫。
9. **動工前先確認網站有沒有全站 Custom Footer Page**，有的話頁尾改在那一頁，不要在目標頁再貼一份（會出現兩份頁尾）。見 `references/layout-troubleshooting.md` 最後一節。

## 操作步驟

1. 登入後台。先看一眼目標頁現有內容（用 REST API 讀），抓既有的色碼和 id 命名風格，讓新內容一致。
2. 確認有沒有 Custom Footer Page。
3. 對照設計圖，把每個視覺區塊依序轉成短碼（參考 shortcode-map.md），完成核心規則第 8 條的自我檢查。
4. 用 REST API 寫入（新頁面用草稿；已上線頁面維持原狀態）。
5. 開前台逐區塊和設計圖比對：標題、按鈕文字、顏色、區塊順序、圖片位置。滿版、透明 header 這類效果用 JS 量測確認（`getBoundingClientRect()`），不只看截圖。有落差就修正、寫入、再比對，直到一致。
6. 回報：改了哪一頁、怎麼驗證的（附截圖更好）、還有什麼沒辦法處理（看不清楚的文字、缺素材的圖片、需要設計提供透明素材的不規則形狀）。

設計圖橫跨多個頁面時，各自找到對應頁面分別處理，不要混在同一頁。

## 不適用的情況

- 不是 Enfold 主題：短碼對照不適用，但逐字照抄、Hero 不留空、備註不上線、自我檢查這些規則仍然適用。
- 環境無法操作瀏覽器：改走「設計圖 → JSON → 短碼檔 → 人工貼上」的間接流程。
- 部落格文章列表或要送出資料的表單：不手寫內容或表單邏輯，交給 WordPress 文章功能（`av_magazine`）和表單外掛（Contact Form 7）。
