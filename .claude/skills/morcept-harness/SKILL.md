# Morcept 工作準則（Harness）

2026-07 建制、2026-10 更新。目的：不論哪個模型、哪個環境，在 Pipi 的專案裡都用同一套程序穩定產出。準則的價值在於把「判斷」換成「可檢查的步驟」——跑程序，不靠感覺。

## 先看你在哪個環境

| 環境 | 適用範圍 |
|---|---|
| claude.ai 對話 / 手機 App | 核心規則全部適用。沒有 subagent：大量讀取自己做，回覆只寫結論；驗收用 references/judgment.md 第 5 節的最低驗法自審。 |
| Cowork（桌面 App） | 核心規則全部適用。可以派 subagent 的話，依環境規定（通常要使用者同意）再派；否則同上。 |
| Claude Code | 全部適用。專案根目錄有 CLAUDE.md + ops/ 時以專案檔為準（本 skill 是它的鏡像）。 |

## 核心規則

這幾條都是踩過坑才訂的，括號內是原因。

1. **改既有檔案前先備份**：`cp file file.bak-$(date +%Y%m%d)`，新內容寫新檔。（沒有備份，改壞就只能憑記憶重建。）
2. **大型 HTML（超過 500 行）不整檔重寫**，用錨點替換。改完驗證：`grep -c "<script"` 和 `grep -c "</script"` 數量相等、檔尾有 `</html>`。JS 字串裡的 `</script>` 寫入前換成 `<\/script>`。（曾經靜默截斷，到客戶端才發現。）
3. **完成 = 驗收清單逐條 PASS**，不是「程式碼寫完了」。說得出「應該可以」就代表還沒驗。判準見 references/judgment.md 第 2 節。
4. **品味題和模糊題不自己決定**：視覺風格、文案語氣、兩種合理解讀會做出不同結果時，給 2–3 個選項讓 Pipi 選。（一次確認比三次返工便宜。）判準見 judgment.md 第 3、6 節。
5. **不可逆的動作先問**：刪檔、動 Firebase 正式庫、改線上客戶資料、寄出通知。
6. **不確定就查，查不到就標「未確認」**。人名、金額、日期、路徑這四類事實，每次都回到來源核對，不要從記憶摘要直接寫進交付物（記憶可能過期）。
7. **踩坑要記錄**：用 references/maintenance.md 第 3 節的五欄格式。寫不出可以執行的修法，就先不要寫。

## 每次任務的節奏

- **開場**：確認任務；需求模糊就照規則 4、5 判斷要不要先問。專案有 STATE.md 就先讀。
- **執行**：守核心規則；環境允許時，大量讀取交給 subagent。
- **收尾**：實際驗收（不是自我感覺）→ 有坑就寫教訓 → 更新 STATE.md → 用一段話總結：改了什麼／怎麼驗的／還剩什麼。
