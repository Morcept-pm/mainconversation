# judgment.md — 判斷力外化 Rubric

> 用法：拿不準時查對應節，逐條比對訊號。符合 2 條以上就照建議動作執行，不要再猶豫。

## 1. 何時該升級模型
**優先序：dispatch.md 第 4 節的硬規則先行**（Haiku 錯 1 次即升級、Sonnet 連錯 2 次即升級，不需湊訊號）。本節處理硬規則沒涵蓋的模糊情況。
**升級訊號（符合任 2 條 → 升級）：**
- 已按 dispatch.md 第 4 節重試過且帶了失敗軌跡，仍錯
- 任務需要「跨 3 個以上檔案/模組同時推理」才能判斷對錯
- 錯誤是「行為不符預期但沒有錯誤訊息」（靜默錯誤最吃推理力）
- 任務涉及取捨且取捨標準不明確（例：效能 vs 可讀性、改動範圍 vs 風險）

✅ 正例：獎金計算結果偏差，Sonnet 改了兩次公式都不對，且沒有報錯 —— 靜默錯誤 + 兩次失敗 → 帶軌跡升 Opus。
❌ 反例：Haiku 批次改檔漏了一個檔案 —— 這是機械疏漏不是能力不足，補派同型號補做即可，升級是浪費。

## 2. 何時算真的完成（Definition of Done）
**全部成立才算完成：**
- 驗收清單逐條 PASS，且由 fresh-context 驗收者確認（不是執行者自己說；沒有 subagent 的環境改用第 5 節最低驗法逐條自審並附證據）
- 產物已落檔在講好的路徑，read-back 讀得到、內容完整
- 大型 HTML 過 verify_html.py；有測試的程式碼測試綠
- STATE.md 已更新（專案有 STATE.md 時）
- 對使用者的總結寫好：改了什麼 / 怎麼驗的 / 剩什麼

✅ 正例：改完模板 → 驗收 agent 重讀檔案逐條核對 → tag 平衡驗證通過 → STATE.md 更新 → 回報。完成。
❌ 反例：「程式碼已修改完成，應該可以正常運作了」—— 有「應該」二字就不是完成。沒驗 = 沒做完。

## 3. 何時該停下來問使用者
**先自查再問**：問題答案若在 STATE.md、LESSONS.md、程式碼註解或 git log 裡，自己找。
**必須問（任 1 條成立就問，不要猜）：**
- 動作不可逆或影響真實對外資料（刪檔、改線上客戶資料、動 Firebase 正式庫、寄出通知）
- 兩種合理做法會產生使用者可感知的不同結果（例：權限規則兩種解讀、金額四捨五入方式）
- 需求與 STATE.md 記載的已定決策矛盾
- 涉及品味與偏好（視覺風格、文案語氣、對客戶的措辭）—— 這類做 2-3 個選項讓使用者挑，不要自行定奪

**不要問（自己決定並在回報中註明假設）：**
- 純技術實作細節（變數命名、內部結構）
- 有明顯業界慣例的選擇
- 問了也只會得到「你決定就好」的問題

✅ 正例：「維運人員 Jessie 的獎金規則有兩種解讀，分別算出 3200 和 4100」→ 停下來問，附兩種算式。
❌ 反例：「請問函式要叫 calcBonus 還是 calculateBonus？」→ 不要問，選一個，做完講一聲即可。

## 4. 方向錯了的訊號（該換路，而非重試）
**換路訊號（符合任 2 條 → 停止重試，換方法或回報）：**
- 每修一個問題冒出一個新問題，連續 3 次
- 修正需要的「例外處理 / 特判」越加越多
- 開始需要對抗工具或框架的預設行為才能前進
- 回頭看：目前做法和最初目標的連結已經說不清楚

換路的動作順序：(1) 停手 → (2) 用三行寫下「原目標 / 目前路徑 / 為什麼走到這」→ (3) 提出一條不同路徑 → (4) 若新路徑動到已定決策，按第 3 節問使用者。

✅ 正例：為了讓 WebGL uniform int 在某瀏覽器動起來，連寫三個 workaround 都出新 bug → 停，換成 uniform float + 範圍比較（LESSONS 已有此坑）。
❌ 反例：測試失敗一次就整個換框架 —— 單次失敗先看失敗軌跡，換路需要 2 條以上訊號。

## 5. 品質底線怎麼驗
**最低驗法（任何交付不得低於此）：**
- HTML/JS：verify_html.py 通過 + 實際開啟一次（headless 亦可）console 無紅字
- 資料/計算：抽 2 筆邊界案例手算核對（最大值、零/空值）
- 文件：read-back 後檢查「使用者名字、金額、日期、路徑」四類事實與來源一致
- 任何「我覺得沒問題」都必須能指出對應證據（測試輸出、比對結果、檔案:行號），指不出來就是沒驗

✅ 正例：獎金表交付前抽 Annie（最高業績）與新人（零業績）兩筆手算比對。
❌ 反例：「表格公式我檢查過邏輯是對的」—— 沒有抽樣比對輸出，只是重讀了一次自己的公式。

## 6. 誠實條款：這套 rubric 補不了的東西
拆解、驗證、多樣本評審能把**執行品質**拉高；但以下兩類靠程序補不了，遇到照指示辦：
- **模糊題**（需求本身沒說清楚、成功長什麼樣沒人知道）：不要硬做。產出「問題清單 + 2-3 個方案草圖」給使用者選，成本最低。
- **品味判斷**（美感、語氣、策略取捨）：任何模型的品味都可能偏離 Pipi 和客戶的期待，而且自己察覺不到。做法依序：(a) 給多個選項讓使用者挑 (b) 環境允許時請更高等級模型出第二意見 (c) 仍拿不準就明說「這題超出我能可靠判斷的範圍」。明說做不到，永遠比假裝做得到好。
