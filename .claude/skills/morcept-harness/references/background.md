# background.md — 準則的由來與環境風險

2026-07-03 首次建制時，從長期對話紀錄歸納出這個環境最常出事的三個地方。2026-10 更新為不綁定特定模型的版本，內容保留，只拿掉過時的型號與環境假設。

## 風險一：巨型單檔 HTML 被整檔讀入、整檔重寫（證據強度：高）

- 產檔工具（base64 內嵌五種模板）、integrated-bonus.html、design-worklog.html、客戶教學系統 v4 都是萬行等級的單檔。
- 實際事故：JS 字串內 `</script>` 沒跳脫、script 標籤數不平衡 → 輸出被**靜默截斷**，到客戶端才發現。
- 整檔重寫的成本：讀一次加寫一次就是兩萬行；長輸出的尾端最容易漏內容，而且截斷不會報錯。

**做法：**
1. 改既有大檔一律錨點替換（Edit 工具或 Python 字串替換），一次改一個定位點。
2. 改前改後都用固定指令驗證，不用目測：
   ```bash
   grep -c "<script" file.html; grep -c "</script" file.html; wc -c file.html
   # 開閉標籤數要相等；檔案大小的差異要能用改動內容解釋
   ```
3. base64 模板沿用既有的 Python patch 流程：**替換 → decode → 驗證標籤平衡 → re-encode**，四步都不能省。
4. 專案內固化成 `tools/verify_html.py`，改完 HTML 必跑。

## 風險二：主對話直接吞大量原始內容（證據強度：中，屬推斷）

- 症狀：主對話讀進整個大檔、搜尋結果、多輪 debug log → 後段回應變泛、忘記前面的決策、偏離規格。
- 做法：預估要讀超過 300 行、超過 2 個檔案、或任何網頁研究，環境允許就派 subagent，主對話只收結論（細則見 dispatch.md）。長產物落檔、回傳路徑。context 用掉一半以上時，先把目前狀態寫進 STATE.md 再繼續。

## 風險三：專案狀態不落檔，跨 session 靠記憶重述（證據強度：高）

- 症狀：每個新 session 要重新解釋背景；不同 session 對同一份規格理解不一致（權限規則、人員名單、模板行為）；改 A 專案時誤用 B 專案的慣例。
- 記憶摘要會過期、也不受 Pipi 控制；專案裡的檔案才是可控的持久層。
- 做法：每個活躍專案一份 `STATE.md`，固定四節：**現況／已定決策（含理由）／未完成／已知坑**。開工先讀，收工更新。CLAUDE.md 只放路由（哪個專案的狀態在哪），不放內容本體。

## 給接手的模型：三件最重要的事

1. **最大的風險是規格不明時假裝明白。** Pipi 是 PM，需求常用結果描述（「客戶要能看到 SEO 建議」），中間有大量沒講出來的決策空間。動手前把空白變成問題清單或 2–3 個方案，一回合的確認換掉三回合的返工。
2. **這裡的技術重心是單檔巨型 HTML，跟「整檔重新生成」的直覺相衝。** 永遠錨點替換、永遠跑驗證。部署在 Firebase/Vercel 正式環境，工具直接面對客戶與同事的真實資料（獎金金額、權限）；動到計算和權限時，judgment.md 的第二意見機制是保險，不是官僚程序。
3. **記憶會給你過期資訊，檔案才是真相。** 記憶和 STATE.md／程式碼衝突時，以磁碟上的檔案為準，並提醒 Pipi 記憶可能過期。

## 這套準則會怎麼失效、怎麼預防

1. **規則堆積成噪音**：每次踩坑加一條，最後變成沒人遵守的 300 行。→ maintenance.md 第 4 節的精簡觸發；新增規則要 Pipi 核准。刪規則跟加規則一樣重要。
2. **教訓寫成格言**：「要小心」「注意品質」寫進去等於沒寫，還會稀釋真正的教訓。→ 五欄格式是硬性的。
3. **派工和驗收變成表演**：不合約的回報照收、驗收者其實看了執行者的自述。準則失效通常不是被推翻，而是被敷衍。→ dispatch.md 第 5 節「不合約就重派」是底線。
4. **準則跟環境脫節**：模型換代、工具改版後，文件裡的描述變成錯的還在被引用。→ 發現文件和實際環境不符，屬於 maintenance.md 第 1 節「可以自行修正的客觀錯誤」，當場修並告知 Pipi。
