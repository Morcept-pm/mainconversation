# maintenance.md — 準則檔案維護協議

> 路徑說明：在 Claude Code 專案中，準則檔位於 CLAUDE.md 與 ops/；在本 skill 中對應 SKILL.md 與 references/。

> 對象：未來任何 session 的模型。本協議規定你能改什麼、怎麼改、改壞了怎麼救。

## 1. 權限分級
### 可自行修改（改完在回報中告知使用者即可）
- `ops/LESSONS.md`：新增教訓（按第 3 節格式）
- CLAUDE.md 專案索引：新增專案列、更新 STATE.md 路徑
- 修正客觀錯誤：錯字、失效路徑、與實際環境不符的工具名
- 查證後的環境事實（可用型號、工具名稱、路徑）回填到對應文件

### 動之前必須先問使用者（附「現況 / 建議改法 / 理由」三行）
- 刪除或放寬 CLAUDE.md 絕對規則、dispatch.md 升降級門檻、judgment.md 任何 rubric
- 修改驗收相關規定（回報合約、驗證不自驗、DoD）
- 重寫任何 ops/ 檔案的整體結構
- 新增會約束所有未來 session 的新規則（新增規則是有成本的：每條都佔每個 session 的注意力）

### 永遠不改
- background.md 的歷史診斷內容（只能追加「後記：此項已由某日 session 證實／推翻」）
- 任何 .bak 備份檔

## 2. 修改程序（不分級別，一律照做）
1. `cp 目標檔 目標檔.bak-$(date +%Y%m%d)`
2. 錨點式修改（不整檔重寫）
3. read-back：重讀改後檔案確認落地
4. 在檔案底部「變更紀錄」加一行：`日期 | 改了什麼 | 為什麼 | 誰核准（使用者/自行）`

## 3. 教訓寫回：ops/LESSONS.md 格式
每次踩坑，收尾時寫入一條，**五欄缺一不可**：
```
## L-編號（日期）標題一句話
- 情境：做什麼任務、哪個專案
- 錯誤：實際發生什麼（含錯誤訊息原文或具體症狀，禁止寫「出了點問題」）
- 根因：為什麼會錯（不知道就寫「根因未明，症狀繞過法如下」）
- 修法：下次怎麼避免，寫成可執行的指令或檢查步驟
- 升級：這條要不要變成正式規則？(a) 不用，留在 LESSONS (b) 建議入 CLAUDE.md/dispatch/judgment → 按第 1 節流程問使用者
```
反例（禁止）：「要小心處理 HTML 的特殊字元」—— 沒有情境、沒有指令、沒人知道怎麼執行。
正例：「JS 字串含 `</script>` 會提前終結 script 區塊導致靜默截斷；寫入前一律替換為 `<\/script>`；驗證：改後 grep -c 開閉標籤數相等。」

## 4. 精簡觸發（防規則堆積腐化）
任一條件成立時，session 收尾多做一步「提出精簡方案給使用者」：
- CLAUDE.md 超過 120 行
- LESSONS.md 超過 25 條
- 發現兩條規則互相矛盾（立即報告，附兩條原文，由使用者裁決；裁決前以較嚴格者為準）

精簡方法：重複合併、已固化成腳本的教訓改成一行指向腳本、超過 6 個月未再觸發的教訓移到 LESSONS-archive.md（不刪除）。

## 5. 改壞了怎麼救
- 任何檔案行為異常 → 先 diff 最近的 .bak，還原後再議
- 找不到備份 → 明確告知使用者哪個檔可能損壞，不要靠記憶重建內容
