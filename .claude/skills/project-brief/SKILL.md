# 企劃大綱產出

流程：**理解需求 → 補問關鍵資訊 → 產出文件**。

## 第一步：理解需求

輸入可能是一段文字、營運或客戶截圖（直接看圖片內容），或已整理好的需求條列。

讀完先評估兩件事，結果會寫進最後的「風險評估」：
1. **需求是否合理可行**：技術可行性、邏輯合理性、營運風險。
2. **有沒有不建議做的部分**：記下原因和可以調整的方向。

## 第二步：補問（產出前）

產出前先確認一件事，因為答案會改變整份大綱的寫法：

> 這是全新功能，還是既有功能的延伸？

- **既有功能延伸** → 請使用者提供原功能說明或文件，讀完再繼續。
- **全新功能** → 直接產出。

其他缺少的關鍵資訊也可以補問，但一次最多問 2 題，避免讓使用者一次回答一長串。

## 第三步：產出企劃大綱

### 固定結構

```
一、需求概述
二、痛點與解決方向
三、核心方案
四、預期效益
五、風險評估
```

**一、需求概述**：條列
- **名稱**：功能名稱
- **背景**：需求來源（例如客戶、業務、內部流程）
- **描述**：功能目的與調整方向；有「原機制 vs 調整後」就分開寫

**二、痛點與解決方向**：固定用表格，兩欄：左「痛點」、右「解決方向」。
- 歸納成核心問題，不要逐一列每個情境。
- 多個情境的解決方向本質相同（例如都是「新增某功能」）就合併成一列，情境放在補充說明。
- 如果每一列的解決方向都在講同一件事，就是需要再歸納的訊號。
- 以 2～4 列為宜，超過 4 列先檢查能不能合併。

**三、核心方案**：依需求性質自訂子模組，常見是「後台設計」「前台／使用者端設計」。多階段推進就用「第一階段／第二階段」分層。每個子模組條列說明，不要切得太細。

**四、預期效益**：條列
- 定性目標：建立什麼行為模式或體驗
- 定量指標：預期提升哪些數據
內容複雜時可以加表格。

**五、風險評估**：這一節一定要有。
- 全部合理可行 → 寫「目前無明顯風險，建議正常推進」。
- 有不建議做的部分 → 寫清楚哪一項、原因（技術／邏輯／營運）、可替代的方向。

## 用語

- 用客戶和網站／行銷業界習慣的說法，例如「使用者／訪客」「後台」「會員」；沒把握時沿用需求原文的用詞。
- 同一個概念全文用同一個詞，不混用。

**語氣**
- 精簡精確，不冗長。
- 避免中英夾雜（ROI、SEO、VIP 等業界固定用法除外）。
- 沒有具體數字時寫「預期提升」，不要編數字。

## 輸出格式

- 格式 `.docx`。環境裡有 docx skill 時先讀它的 SKILL.md，照它的做法產出。
- 字體全文用 `Microsoft JhengHei`（微軟正黑體）。
- 不加文件標題，直接從「一、需求概述」開始。
- 大節用 Heading 1，節內子標題用 Heading 2。
- 表格欄寬平均分配，表頭底色淺藍 `D5E8F0`。
- **一行只說一件事**：有多個重點就展開成子項目，每點一行；只有一個說明就接在同一行。一行裡不要塞三個以上重點。
- 用當下環境的檔案交付方式提供檔案。
